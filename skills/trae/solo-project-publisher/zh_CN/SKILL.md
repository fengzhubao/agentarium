# SOLO Project Publisher

使用这个 Skill，帮助开发者把真实项目工作流发布成可信的社区帖子或项目报告。

输出必须基于文件、命令、截图、改动差异或生成物等证据。不要写没有证据支撑的宣传式结论。

## 适用场景

- 已经做完一个功能、工具、脚本或项目阶段，需要发布社区帖。
- 想参加比赛或活动，需要把创作过程、使用步骤和效果展示整理清楚。
- 需要把本地仓库里的真实证据整理成项目报告、Release 说明或技术案例。
- 需要在发布前检查是否含有敏感文件、私有链接或不可公开内容。

## 不适用场景

- 用户只想写一篇没有项目证据支撑的营销文。
- 用户要求编造截图、测试结果、用户反馈或源码链接。
- 目标材料主要是个人信息、隐私数据、客户数据、内部事故细节，且没有明确脱敏边界。
- 用户要求读取或展示认证文件、密钥、Cookie、Token、私钥等敏感内容。

## 推荐输入

用户最好提供这些信息：

```text
目标目录：<项目目录或仓库路径>
发布渠道：<论坛、社区、Release、内部报告等>
公开边界：<哪些能公开，哪些不能公开>
演示目标：<希望读者看完后理解什么>
已有证据：<截图、命令、文件、链接、生成物等>
```

如果用户没有给完整信息，可以先从当前目录、仓库状态和已有文档推断；只有公开边界或发布目标不清楚时再提问。

## 工作流程

1. 界定范围
   - 确认目标项目、仓库或目录。
   - 确认目标读者和发布渠道。
   - 只有公开边界不清楚时才提问；否则按保守原则推断。
   - 记录不能公开的内容。

2. 检查材料
   - 优先读取最相关的本地文档和改动文件。
   - 如果有仓库，就检查仓库状态。
   - 寻找命令、脚本、生成物、截图和验证输出。
   - 避免读取或引用 Token、认证文件、私钥、凭证备份等敏感文件。

3. 整理证据
   - 用一个短段落总结真实场景。
   - 把过程提炼成具体步骤。
   - 为每个重要结论收集证据。
   - 区分已完成结果和计划中的后续工作。

4. 起草内容
   - 使用目标渠道要求的结构。
   - 如果是 TRAE SOLO 技能创作赛，应包含：
     - Skill 简介
     - 使用场景
     - 创作过程
     - 使用步骤
     - 效果展示
     - Skill 链接
     - 总结与思考
   - 面向中文社区时，默认输出简洁中文，除非用户另有要求。

5. 发布前复查
   - 检查是否含有密钥、私有主机名、私有仓库链接、个人姓名、账号、邮箱、头像、Token 或不必要的本地绝对路径。
   - 检查每个关键结论是否有证据。
   - 标记仍需补充的截图、公开链接或最终 Skill 市场链接。
   - 给出简短的下一步清单。

## 证据要求

每篇输出至少尝试包含 3 类证据：

- 过程证据：操作步骤、提示词片段、创作过程截图或对话摘要。
- 结果证据：生成文件、Skill 包路径、输出草稿、命令结果或目录变化。
- 可信度证据：公开链接、校验命令、使用前后对比、人工复查结论。

如果证据缺失，不要编造；用 `[待补]` 明确标记。

## 敏感信息规则

- 不要读取 `auth.json`、`.env`、私钥、Token、Cookie、账号密码文件。
- 不要贴出内部主机名、私有仓库地址、客户名称、个人姓名、真实账号、邮箱、头像、用户标签或机器指纹。
- 公开输出默认使用相对路径或脱敏占位；只有非公开内部报告且有明确理由时才保留本地绝对路径。
- 如果输出面向公开社区，必须先给出“发布安全检查”。

## 输出结构

如果目标是比赛或社区帖子，输出：

```markdown
# 〖Skill 创作〗<Skill 名称或一句话描述>

## 1、Skill简介

## 2、使用场景

## 3、创作过程

## 4、使用步骤

## 5、效果展示

## 6、Skill 链接

## 7、总结与思考
```

如果目标是内部报告，可以调整为：

```markdown
# 项目案例

## 背景

## 改动内容

## 证据

## 验证

## 风险

## 下一步
```

## 参考材料

- 需要复用帖子骨架时，读取 `references/post-template.md`。
- 需要做证据和公开安全检查时，读取 `references/evidence-checklist.md`。

## 最小试跑清单

第一次试跑时，至少输出：

- 一篇按 7 段结构组织的参赛帖草稿。
- 一个“待补材料”列表。
- 一个“发布安全检查”列表。
- 一个“下一步修改 Skill 的建议”列表。
